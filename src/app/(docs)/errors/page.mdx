# Errors

Arche returns machine-readable JSON errors so failed requests can be retried, routed, or escalated programmatically.

## Error Envelope

Representative error response:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "http_status": 400,
    "message": "from must be <= to",
    "details": {},
    "trace_id": "req-123"
  }
}
```

Field meanings:

- `code`: stable machine-readable classification
- `http_status`: HTTP status that should drive retry or fallback behavior
- `message`: operator-facing detail for logs and debugging
- `details`: structured context for the error, an empty object when there is none
- `trace_id`: Arche-generated request identifier to include when escalating an issue

Every error carries all five keys. `details` and `trace_id` are present even
when empty or null, so one parser handles every error body.

If you sent an `X-Request-ID` header, Arche echoes it back on the response, so a
failed call has two identifiers: yours and ours. See
[Request IDs](/troubleshooting/request-ids) for how to set them and which to
quote when escalating.

## Status Codes

The public schema documents route-level error statuses including:

- `400` for invalid parameters or malformed requests
- `401` for missing or invalid authentication
- `403` for unauthorized access, and for anything your plan does not include
- `404` when a requested resource cannot be found
- `429` when the request budget is exceeded

## Plan Limits Return 403

A capability your plan does not include returns `403` with the code
`FEATURE_NOT_AVAILABLE`, not an empty result. The `details` name what is
required and what you hold:

```json
{
  "error": {
    "code": "FEATURE_NOT_AVAILABLE",
    "http_status": 403,
    "message": "This feature requires the growth plan or higher.",
    "details": { "required_tier": "growth", "current_tier": "developer" },
    "trace_id": "…"
  }
}
```

This covers two cases that look different but are the same refusal:

- an endpoint your plan does not include, such as deterministic replay below
  Growth
- a **company outside your plan's coverage** — Free covers the Dow 30 and
  Developer the S&P 500, so a request for any other filer is refused rather
  than answered empty

Treat it as a configuration outcome, not a transient failure. Retrying will not
change it, and an empty-result fallback will silently hide it. Branch on
`details.required_tier` if you need to surface an upgrade path. See
[Rate limits](/rate-limits) for what each plan includes.

## Absent Is Not Failed

A request that finds nothing is answered, not failed. Two cases are easy to
confuse and are reported differently:

- A statement identity that exists but was never restated returns `200` with an
  empty restatement timeline: `total_hops` is `0`, `by_metric` is empty and
  `timeline_severity` is `NONE`. A filer reporting a period once is ordinary
  history. This is also what a period returns when two versions differ in no
  metric.
- A statement identity with no versions at all returns `404`
  `EDGAR_STATEMENTS_NOT_FOUND`.

Neither is a server fault, and neither should be retried. Earlier releases
reported the first case as `502`, which made ordinary reporting history look
like an upstream outage.

## Troubleshooting

- Log the request path, query parameters, response status, `trace_id`, and the `X-Request-ID` you sent.
- Treat `400` responses as caller bugs to be fixed before retry.
- Treat `429` responses as backoff signals rather than permanent failures.
- Preserve the original request inputs when debugging point-in-time discrepancies.
- Follow [Request IDs](/troubleshooting/request-ids) when you need to escalate.
